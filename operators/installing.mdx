---
title: "Installing OMNI on your own server"
description: "How to install a FireFlo OMNI release on a Linux server you run, put its two domains behind TLS, choose its modules, and upgrade it."
---

An OMNI release is one file per processor type. It carries the API, the panel and every
channel, battery and plugin, with its own Python and Node.js, so the server needs no build
tools and downloads nothing while it installs. You choose which modules the server runs at
install time, and change that later on the server.

Releases are delivered by FireFlo under your licence. Ask
[support@fireflo.au](mailto:support@fireflo.au) for the current release and its files.

## Before you begin

| | Requirement |
| --- | --- |
| **Processor** | Linux on x86-64, or aarch64 (ARM, such as AWS Graviton). There is one release file for each |
| **Operating system** | Ubuntu 22.04, 24.04 or 26.04, or Debian 12 or 13, with systemd and root access |
| **PostgreSQL** | 14 or newer, with the `pg_trgm` extension, and `pgvector` when AI Agents or Calendar is loaded |
| **Redis** | 6 or newer, or Valkey |
| **Domains** | two names pointing at the server: one for the API and one for the panel. They can't share a name |
| **In front** | a reverse proxy with TLS, such as nginx, Apache or Caddy, which you set up |

The release files are:

- the release itself, `fireflo-omni-<version>-single-amd64.tar.gz` or `…-arm64.tar.gz`;
- `SHA256SUMS` and `SHA256SUMS.asc`, its checksum and FireFlo's signature over it;
- `SIGNING-KEY.asc`, FireFlo's public signing key;
- `setup.sh`, which installs the services OMNI needs on a fresh server.

## Install

<Steps>
  <Step title="Copy the files to the server">
    ```bash
    scp fireflo-omni-<version>-single-amd64.tar.gz SHA256SUMS SHA256SUMS.asc SIGNING-KEY.asc setup.sh root@your-server:/root/
    ```
  </Step>
  <Step title="Verify them">
    The checksum proves the download is intact; the signature proves it came from FireFlo.

    ```bash
    gpg --import SIGNING-KEY.asc
    gpg --verify SHA256SUMS.asc SHA256SUMS
    sha256sum -c SHA256SUMS
    ```

    Check the key's fingerprint rather than trusting the file beside the release:
    `3A9B 256F DE50 75CA 5F76  ADAF 42D7 A01A ED0D 03BA`.
  </Step>
  <Step title="Prepare the server">
    `setup.sh` installs PostgreSQL with `pgvector` and `pg_trgm`, and Redis. It creates no
    database, role or password. `--dry-run` shows what it would do.

    ```bash
    sudo ./setup.sh --dry-run
    sudo ./setup.sh
    ```
  </Step>
  <Step title="Unpack and install">
    Type the two passwords at prompts and put them in an answers file only root can read,
    so neither appears in the shell history or the process list:

    ```bash
    read -rsp 'Database password: ' DB_PW; echo; read -rsp 'Admin password: ' ADMIN_PW; echo
    sudo install -m 600 /dev/null /root/omni-answers.env
    printf 'DB_PASSWORD=%s\nADMIN_PASSWORD=%s\n' "$DB_PW" "$ADMIN_PW" | sudo tee /root/omni-answers.env >/dev/null
    ```

    Then one command installs everything:

    ```bash
    tar xzf fireflo-omni-<version>-single-amd64.tar.gz && cd fireflo-omni-<version>-single-amd64
    sudo ./install.sh --env-file /root/omni-answers.env --modules all \
      --api-domain api.example.com --panel-domain app.example.com \
      --db-name omni --db-user omni \
      --admin-email you@example.com --admin-name "Your name"
    sudo rm /root/omni-answers.env
    ```

    Name the modules instead of `all` to run only some, for example `--modules
    sms,whatsapp,crm`. A module that needs another brings it, and the installer says so.
    A set that couldn't start is refused before anything is installed.
  </Step>
  <Step title="Put a reverse proxy in front">
    The installer writes no web-server configuration. The API and the panel listen only on
    the server itself, and your reverse proxy forwards each domain to its port. The
    installer prints the same list when it finishes.

    | Domain | Forward to, on the server itself | Request bodies up to |
    | --- | --- | --- |
    | the API's, over HTTPS | port 8200 | 215 MB, for audience uploads |
    | the panel's, over HTTPS | port 3200 | 6 MB |

    For both domains:

    - serve HTTPS only. The panel's sign-in cookie is secure-only, so over plain HTTP
      nobody stays signed in;
    - pass the `Host` header through unchanged;
    - set `X-Forwarded-Proto: https`, `X-Forwarded-For` and `X-Real-IP`;
    - use HTTP/1.1 to the backend with a read timeout of at least 65 seconds, and leave
      redirects as they are.

    Webhooks from SMS gateways and Meta arrive on the API's domain, so it must be reachable
    from the internet over HTTPS. See [An nginx configuration](#an-nginx-configuration)
    for a complete example.
  </Step>
  <Step title="Sign in">
    Open the panel's domain and sign in as the admin address you gave. That login is
    platform staff: it sees the **Platform** section, where you set up products, prices
    and channel connections. See [Running OMNI for your customers](/operators/overview).
  </Step>
</Steps>

### What the installer asks for

Anything you leave out is asked for, or read from an answers file given with
`--env-file` (the release carries an example with every key). A flag given on the command
line wins over the same key in the file.

| Flag | What | Default |
| --- | --- | --- |
| `--modules` | the channels, batteries and plugins to run, or `all` | asked |
| `--api-domain`, `--panel-domain` | the two domains | asked |
| `--db-host`, `--db-port`, `--db-name`, `--db-user` | the database; its password is `DB_PASSWORD` in the answers file. Or one `--database-url` | this server, `5432`, `omni`, `omni` |
| `--redis-url` | Redis | the local one |
| `--admin-email`, `--admin-name` | the first staff login. Its password is `ADMIN_PASSWORD` in the answers file | none |
| `--prefix` | the folder OMNI is installed in | `/opt/fireflo` |
| `--user` | the Linux user the services run as, created if missing | `omni` |
| `--api-port`, `--panel-port` | the ports the API and the panel listen on, on the server itself | `8200`, `3200` |

**The database.** With PostgreSQL on the same server, the installer creates the role and
the database when they're missing, with both extensions. A role that already exists keeps
its password, so give the one it has. With PostgreSQL on another server, create the role,
the database and both extensions there first. `--no-create-db` skips the creating
altogether.

<Warning>
  Back up `/opt/fireflo/shared/.env` (`<prefix>/shared/.env` with `--prefix`). Its secret
  key encrypts the provider credentials OMNI stores, such as SMS logins and WhatsApp
  tokens. Without it, those can't be read again, and a restored database won't send.
</Warning>

## Install under a hosting account

On a server where each site lives under its own Linux user, such as the account behind a
virtual host, OMNI can live inside that account and run as that user. Give the folder
with `--prefix` and the user with `--user`:

```bash
sudo ./install.sh --prefix /srv/acme/omni --user acme \
  --env-file /root/omni-answers.env --modules all --yes
```

The user isn't created when it already exists, and its home is left as it is. OMNI's
services are system services that run as that user.

<Warning>
  Upgrade with the same folder **and** the same user:
  `sudo ./upgrade.sh --prefix /srv/acme/omni --user acme`. Without `--user`, an
  upgrade runs the services as the default `omni` user instead.
</Warning>

If the virtual host's web server is managed by a hosting control panel, that panel owns
its configuration files. Put the proxy settings below into the panel's custom
configuration for each domain rather than into your own file, which the panel may
overwrite.

## An nginx configuration

A complete configuration for both domains, with Let's Encrypt certificates. Replace
`api.example.com` and `app.example.com` with your two domains; both must already point at
the server.

<Steps>
  <Step title="Get a certificate for both domains">
    ```bash
    sudo apt install -y nginx certbot python3-certbot-nginx
    sudo certbot certonly --nginx -d api.example.com -d app.example.com
    ```
  </Step>
  <Step title="Write the configuration">
    Save it as `/etc/nginx/sites-available/omni.conf`:

    ```nginx
    map $http_upgrade $omni_connection_upgrade {
        default upgrade;
        ''      close;
    }

    # plain HTTP only sends people to HTTPS and lets certbot renew
    server {
        listen 80;
        listen [::]:80;
        server_name api.example.com app.example.com;
        location /.well-known/acme-challenge/ { root /var/www/html; }
        location / { return 301 https://$host$request_uri; }
    }

    # the API
    server {
        listen 443 ssl;
        listen [::]:443 ssl;
        http2 on;
        server_name api.example.com;

        ssl_certificate     /etc/letsencrypt/live/api.example.com/fullchain.pem;
        ssl_certificate_key /etc/letsencrypt/live/api.example.com/privkey.pem;
        include /etc/letsencrypt/options-ssl-nginx.conf;
        ssl_dhparam /etc/letsencrypt/ssl-dhparams.pem;

        client_max_body_size 215m;

        location / {
            proxy_pass http://127.0.0.1:8200;
            proxy_http_version 1.1;
            proxy_set_header Host              $host;
            proxy_set_header X-Forwarded-Proto https;
            proxy_set_header X-Forwarded-For   $proxy_add_x_forwarded_for;
            proxy_set_header X-Real-IP         $remote_addr;
            proxy_set_header Upgrade           $http_upgrade;
            proxy_set_header Connection        $omni_connection_upgrade;
            proxy_redirect off;
            proxy_read_timeout 120s;
            proxy_send_timeout 120s;
            proxy_request_buffering off;
        }
    }

    # the panel
    server {
        listen 443 ssl;
        listen [::]:443 ssl;
        http2 on;
        server_name app.example.com;

        ssl_certificate     /etc/letsencrypt/live/api.example.com/fullchain.pem;
        ssl_certificate_key /etc/letsencrypt/live/api.example.com/privkey.pem;
        include /etc/letsencrypt/options-ssl-nginx.conf;
        ssl_dhparam /etc/letsencrypt/ssl-dhparams.pem;

        client_max_body_size 6m;

        location / {
            proxy_pass http://127.0.0.1:3200;
            proxy_http_version 1.1;
            proxy_set_header Host              $host;
            proxy_set_header X-Forwarded-Proto https;
            proxy_set_header X-Forwarded-For   $proxy_add_x_forwarded_for;
            proxy_set_header X-Real-IP         $remote_addr;
            proxy_set_header Upgrade           $http_upgrade;
            proxy_set_header Connection        $omni_connection_upgrade;
            proxy_redirect off;
            proxy_read_timeout 120s;
            proxy_buffering off;
        }
    }
    ```

    Certbot saves the one certificate for both names under the first one, so both blocks
    point at `api.example.com`. Change the ports if you installed with `--api-port` or
    `--panel-port`.
  </Step>
  <Step title="Turn it on">
    ```bash
    sudo ln -s /etc/nginx/sites-available/omni.conf /etc/nginx/sites-enabled/
    sudo nginx -t && sudo systemctl reload nginx
    ```
  </Step>
  <Step title="Check it from outside">
    ```bash
    curl -s -o /dev/null -w "API %{http_code}\n" https://api.example.com/api/health/
    curl -s -o /dev/null -w "panel %{http_code}\n" https://app.example.com/login
    ```

    Both should answer `200`.
  </Step>
</Steps>

<Note>
  `http2 on;` needs nginx 1.25.1 or newer. On an older nginx, remove that line and write
  `listen 443 ssl http2;` instead.
</Note>

## Choose modules on the server

```bash
sudo fireflo-omni modules list
sudo fireflo-omni modules enable tickets calendar
sudo fireflo-omni modules disable tickets
```

Enabling a module brings along what it needs, runs its database changes and switches it on.
Disabling switches it off and keeps its data. Either restarts the services for a few seconds.
**Platform → Modules** in the panel shows the same switches, and is where a module's data is
backed up and removed. See [Modules](/operators/modules).

Loading a module gives it to no one yet: customers get it through their product, or one at
a time from their page under **Platform → Customers**.

## Upgrade to a new release

Copy the new release to the server, verify it as above, then:

```bash
tar xzf fireflo-omni-<new-version>-single-amd64.tar.gz && cd fireflo-omni-<new-version>-single-amd64
sudo ./upgrade.sh
```

The server keeps its modules, ports, bind address and settings. An install made with
`--prefix` or `--user` upgrades with the same flags (see
[Install under a hosting account](#install-under-a-hosting-account)). The new release installs beside the running one,
applies its database changes, switches over and restarts in stages: the API, then the
panel, then the background workers, waiting for each to answer. **If one isn't healthy
within 180 seconds, it switches back** to the release that was running
(`--health-timeout` changes the wait). Database changes only ever add, so switching back is
safe. The last three releases are kept.

Take a database dump before an upgrade all the same:

```bash
sudo -u postgres pg_dump -Fc omni > /root/omni-before-upgrade-$(date +%F).dump
```

`sudo fireflo-omni status` shows what runs, and `sudo fireflo-omni logs` its recent logs.

## ARM servers

The ARM release carries the panel ready to build rather than built, because the panel's
server packages are compiled for one processor type. `install.sh` builds it on the server
with the Node.js inside the release, which adds a few minutes to the install and to each
upgrade. Nothing else differs.

## Without root

`--user-mode --prefix ~/omni` installs under your own home and runs OMNI as your user's
services, with no root at all. It suits a trial or a staging server. The database must
already exist, because creating one needs PostgreSQL's administrator.
